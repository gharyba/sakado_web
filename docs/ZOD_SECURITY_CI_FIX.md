# Zod security fix and CI validation

Date: 2026-10-24. Branch: `feat/cinematic-redesign-04`. Baseline HEAD: `6a567bd` (`test: fix Phase 04 lazy image readiness race`). Scope: Zod dependency and lockfile only; no application code, workflow, database schema, media permission, or Redesign 04 behavior changed.

## Cause and change

The pull-request quality job runs `npm ci` and then `npm audit --omit=dev --audit-level=high`. The original direct dependency was `zod: ^4.1.0`; the lockfile and installed tree held one deduplicated `zod@4.6.5`. GitHub advisory [GHSA-mrhx-c7xc-m3w5](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5) marks versions below 4.6.6 affected, so the locked install caused the high-severity audit failure.

`package.json` and the lockfile root now specify `zod: ^4.6.6`. npm generated the single `node_modules/zod` lockfile record at **4.6.6**, including its registry URL and integrity hash. `npm ls zod --all` and `npm explain zod` show one installed, deduplicated **4.6.6** copy; `eslint-plugin-react-hooks` and `zod-validation-error` accept Zod 4. Next.js remains declared and locked at **16.4.1**. No override or other dependency upgrade was added. The Phase 04 browser-test fix and its report remain unchanged.

## Limits and CI follow-up

The upstream [4.6.6 change](https://github.com/colinhacks/zod/pull/6652) checks declared array, set, and map size bounds before parsing elements. Several SAKADO internal settings and media metadata schemas have arrays without `.max()`. This dependency fix clears the reported package-version finding; it does not establish that every untrusted input path has an appropriate body or collection size limit. Review that separately if those schemas become reachable with oversized untrusted input.
