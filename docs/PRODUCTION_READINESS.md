## Review and release workflow

Work on feature branches; open a PR into main after explicit push authorization. Require a human review and both checks from `ci.yml`: **Quality, Tests, Build and Media Safety** and **PostgreSQL Integration and Admin Workflows**. Do not develop directly on main, force-push main, or apply repository settings automatically. GitHub may prefix check names with the workflow name; select the exact checks after their first real run.

In GitHub: Settings → Branches → Add branch protection rule → pattern `main` → require a pull request, at least one approval, dismiss stale approvals, require the two status checks and resolution of conversations, prevent force pushes and deletion. Apply equivalent repository rulesets if the repository UI uses them. Restrict bypass permissions through an explicit owner decision. No GitHub settings were changed in this phase.

CI uses read-only repository permissions, pinned checkout/setup-node commits, npm cache only, `npm ci`, and fixed non-production inputs. No production/staging secrets or database state are cached. Integration services are ephemeral PostgreSQL 16, with identity/directory guards before any fixture deletion. No test traces/participant data are uploaded as public artifacts. The PostgreSQL image is version-major pinned (`postgres:16`), not digest pinned; review and pin a tested digest in the supply-chain process. No deployment job exists.

Exact release prerequisite: review Phase 06 locally, authorize a separate push/PR, observe real Linux CI, then resolve all human and staging gates before any separately authorized deployment.
